# Delta evidence logging

**Verified within the local tests:** repeated record content can be stored as lossless deltas, decoded back to complete events, and checked through the original authenticated chain. Every event still has a distinct sequence, timestamp, MAC and chain link. Intents, reconciliation, alerts, authority changes and intervention events are never coalesced or discarded. This reduces repeated content and stored bytes, not the number of action receipts or durable writes.

The journal maintains the last complete data object for each event type, with at most 64 type baselines. A delta contains the previous same-type sequence (`base`), changed top-level fields (`set`), and removed fields (`unset`). Unchanged fields inherit their values from that baseline. Arrays and nested objects are replaced as whole values when changed. The encoder selects a delta only when its serialized bytes are smaller than the full representation. After at most 32 consecutive deltas per type, the next event is a full checkpoint. Evicting a baseline also forces a full record.

This removes repeated preserved snapshots during self-containment and repeated fields in noise action receipts and denials. Time, event IDs, causes, outcomes and state changes remain reconstructable. Lease renewals retain their changed deadlines. Compression settings live in the trusted journal implementation; SENTRY has no API to change them.

MACs and chain hashes cover the **encoded** records. Journal verification checks those first, then validates and reconstructs deltas. A missing baseline, wrong base sequence, deleted tail or modified delta is rejected. Baselines and compression counters advance only after durable append succeeds. The emergency evidence path continues to write full standalone records so it does not depend on the primary journal's baselines. Older full records without an encoding marker remain readable.

`readJournal()` and `node src/read-evidence.js <evidence.jsonl>` return reconstructed event payloads for inspection. New controller records are encrypted after compression and signing; `readJournal(path, key)` decrypts them, and the standalone reader uses the opaque key-reference sidecar with the Windows user-bound vault. These decoded payloads are not themselves the signed wire representation; `readJournal()` also returns the original `encoded` row. Inspection does not establish an externally trusted chain head. Live controller verification still provides that check within the existing trust model. Old archive encryption preserves original bytes without retroactive HMAC authentication. See `protection-countermeasures.md`.

Status and Guardian reports expose actual bytes, the equivalent full-record bytes, bytes saved, and the number of delta records. The reference size uses the same event metadata and full-v1 encoding. It is a storage comparison for that run, not a throughput benchmark or proof of DoS resistance. Full-stream reconstruction is required; checkpoints do not establish a separate archive/rotation protocol.
